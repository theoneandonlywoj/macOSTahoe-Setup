# Implement Specs

Implement approved, ready specs in one isolated child session. Never stage, commit, push, edit agent permissions, or persist an approved shell command. A separate reviewed configuration change is required to persist permissions.

## Select Work

1. Treat `docs/specs/NNN-topic/` as a session. With no target, use the `question` tool for a multi-select session picker. Accept an exact directory, numeric prefix, unique slug, or feature path. Ask when ambiguous.
2. Read `decisions.xml`, numbered feature files, and existing `implemented.md` for each selected session.
3. Require root status `written`. Implement only features marked `ready` with user stories, Gherkin scenarios, explicit affected-file actions, and dependencies.
4. Skip blocked, draft, malformed, or fingerprint-current features with a concrete reason. Treat old status rows without fingerprints as stale.
5. Build each dependency closure. Implement dependencies first, then feature-number order. Ask before crossing a session, cycle, missing dependency, or unresolved prerequisite.

Use todos only for multi-step work and keep exactly one item `in_progress` while work remains.

## Plan Verification

Before editing each non-trivial feature:

1. State the behavioral claim established by its user stories, scenarios, and acceptance criteria.
2. Select the narrowest evidence that can prove each distinct claim.
3. Assign each verification claim one owner. Do not duplicate delegated and local checks.
4. Map `Given` to setup, `When` to the trigger, and `Then` to the observable result.

## Implement

1. Inspect relevant repository evidence before editing.
2. Limit edits to `Affected files` plus minimal adjacent integration changes. Report each adjacent edit and ask before broader scope or a different file action.
3. Never edit `decisions.xml` or feature specs. Only `implemented.md` may be written in a spec directory.
4. Ask when a spec is ambiguous, contradicts the repository, has unclear status, dependencies, paths, or criteria, or cannot be verified as written.
5. Treat denied shell commands as final unless the user explicitly requests another attempt. Never modify configuration to avoid a prompt or denial.

## Verify

Inspect final changed files instead of trusting summaries. Run evidence in this order:

1. Run changed-file diagnostics or syntax checks.
2. Run targeted tests for the changed behavior.
3. Run relevant broader repository checks.
4. Exercise the matching user-facing behavior when feasible.

Run every runnable acceptance criterion. In this repository, run `zsh -n` for changed `.zsh` files and `make soft-test` for relevant macOS/Zsh changes. Change executable bits only when the spec requires it.

Fix implementation-caused failures and rerun only failed or invalidated checks. Classify every unsuccessful check as an implementation failure, pre-existing failure, external blocker, or inconclusive evidence. Ask before changing unrelated code. Never claim success from incomplete or inconclusive evidence.

## Record Status

Update one row per feature in `implemented.md`. Preserve unrelated entries. Compute a SHA-256 fingerprint from the exact feature file and `decisions.xml` contents for successful or failed work.

```text
# Implementation status
Generated by /w-implement on <date>
- 01-feature.md: implemented <date> - fingerprint <sha256> - <summary>
- 02-feature.md: skipped <date> - blocked: <reason>
- 03-feature.md: failed <date> - fingerprint <sha256> - <failure>
```

Use `failed` or `interrupted` for partial work. On cancellation, stop, preserve completed edits, record the done/pending boundary when possible, and report it.

Return only implemented files and features, skips and failures, adjacent edits, verification evidence and classification, pending work, and the next step (`/w-commit`). Never stage or commit.
